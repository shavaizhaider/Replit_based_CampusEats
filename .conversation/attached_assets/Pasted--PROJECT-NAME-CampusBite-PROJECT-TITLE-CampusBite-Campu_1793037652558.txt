
PROJECT NAME: CampusBite

PROJECT TITLE:
CampusBite — Campus Café Menu & Food Availability Platform

YOUR ROLE:
Act as a senior full-stack web developer, Python Flask engineer, database designer, UI/UX designer, security engineer, and QA tester.

Your task is to design, implement, test, and prepare a complete, functional web application named CampusBite. This is a university campus café menu and food availability platform.

Do not merely create a landing page or static prototype. Build a working full-stack application with a connected database, real admin functionality, persistent data, validation, responsive design, and an installable Progressive Web App (PWA).

==================================================
1. PROJECT OBJECTIVE
==================================================

CampusBite helps university students check what food is available at their campus café before walking to the café.

Students should be able to:
- View the current day's menu without creating an account.
- Browse menus for upcoming days.
- Select Breakfast, Lunch, or Evening/Dinner.
- View food names, images, descriptions, prices, categories, and serving hours.
- Check current stock status and available quantities.
- See when food availability was last updated.
- Search and filter food according to category and dietary preferences.
- Enter a budget in Pakistani Rupees (PKR) and find affordable food.
- View ingredients, dietary information, and allergen notes.
- Rate food from one to five stars and optionally write a review.
- Install CampusBite on their phone's home screen.
- Access the last cached public menu when offline, with a clear warning that the information may be outdated.

Café administrators should be able to:
- Log in securely.
- Manage food items and categories.
- Create daily and future menu schedules.
- Configure meal times and prices.
- Manage stock quantities and availability.
- View and moderate student reviews.
- Preview the public-facing menu.

The first version supports ONE café only.

Use PKR throughout the application. Display prices in a readable format such as Rs. 250.

Do not implement online food ordering, online payments, delivery tracking, multiple cafés, or AI recommendations. These features are outside the first-version scope.

6. MENU AND MEAL LOGIC
==================================================

The application supports three meal periods:
- Breakfast
- Lunch
- Evening/Dinner

Illustrative times only:
- Breakfast: 7:30 AM to 10:30 AM.
- Lunch: 12:00 PM to 3:00 PM.
- Evening/Dinner: 4:00 PM to 8:00 PM.

These are placeholders. The administrator must be able to configure the actual serving windows.

Do not permanently hardcode the example times as the café's confirmed operating hours.

For every selected date and meal:
- Retrieve only schedules matching the requested date and meal.
- Show the corresponding foods.
- Show the correct serving times.
- Display accurate stock status.
- Display the last-updated timestamp.
- Handle missing schedules gracefully.

An item may be labelled currently available only if:
- The food item is active.
- Its schedule matches the selected date and meal.
- Its quantity is greater than zero.
- The current time falls within the configured serving window, unless advance availability is intentionally enabled.

Future menu items may still be displayed as scheduled, but must not be falsely labelled as currently available before their serving window.

Expired serving windows must not appear as currently available.

Keep date and time logic consistent with the café's local timezone. Avoid comparing incompatible naive and timezone-aware timestamps.

7. LIVE AVAILABILITY AND AUTO-REFRESH
==================================================

Implement near-real-time availability using lightweight JavaScript polling.

Requirements:
- Poll public menu data every 15–30 seconds.
- Prefer 20 seconds as the initial interval.
- Use a Flask JSON endpoint or another simple, reliable server endpoint.
- Return only necessary public fields.
- Update relevant stock badges, quantities, and last-updated timestamps.
- Avoid a complete page reload when possible.
- Prevent overlapping requests.
- Handle network failures gracefully.
- Pause or reduce polling when the browser tab is hidden.
- Resume normal polling when the tab becomes visible.
- Do not show fake real-time updates.

When an administrator updates stock:
1. Validate the submitted change.
2. Save the change in the database.
3. Update the stock timestamp.
4. Return a clear success or error response.
5. Allow student pages to display the new saved values on the next refresh.

Live availability means reflecting saved administrator updates. It does not mean automatically detecting food sales or physically counting inventory.
